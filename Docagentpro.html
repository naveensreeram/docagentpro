⚡ Token Savings — Explained

        
How DocAgentPro minimises AI credits and what the savings counter measures

      

      
    

    
    


      
      

        
Q1
What does the "⚡ N tokens saved" counter actually measure?
▼

        

          
It compares DocAgentPro's optimised API call against what a naive, unoptimised implementation would have sent to the same AI provider — a basic app with flat max_tokens: 8000, no prompt compression, no model routing, no caching, and no input truncation.

          
The counter shows savings vs a naive same-provider call — not vs zero cost. The baseline reflects how most internal tools and quick AI integrations are actually built.

        

      


      
      

        
Q2
Does it compare against using ChatGPT.com or Claude.ai directly?
▼

        

          
Not directly — but the savings still apply and are often larger. ChatGPT.com and Claude.ai send no token budgets, no smart routing, and no prompt compression.

          
ComparisonSaving?

            
DocAgentPro vs naive same-provider app✅ Yes — this is what the counter shows

            
DocAgentPro vs ChatGPT.com / Claude.ai✅ Yes — those send no budgets or routing

            
DocAgentPro free tier (Groq) vs paying OpenAI✅ Massive — $0 vs ~$0.012 per document

            
DocAgentPro vs same API, no optimisation✅ Yes — our layer reduces consumption

            
DocAgentPro vs perfectly hand-optimised app⚠️ Partial — depends on their quality

          

        

      


      
      

        
Q3
How exactly is the saving calculated?
▼

        

          
The estimateGenerationSavings() function computes two numbers every generation and takes the difference:

          
Naive baseline (direct unoptimised call):
  Output tokens:  8,000         ← flat cap, no per-doc budget
  System prompt:  ~400 tokens   ← verbose 6-point requirements block
  Input:          full paste    ← no extraction, up to ~4,000 tokens

DocAgentPro actual:
  Output tokens:  getDocMaxTokens()  ← 1,500 README · 900 exec summary · 3,500 SOP
  System prompt:  ~150 tokens        ← tightened single-line rules
  Input:          smart-extracted   ← high-signal lines only, ~50% fewer tokens

Saving = Naive − Actual → displayed in topbar badge

Q6
Does Anthropic prefix caching need any setup?
▼

        

          
No — applied automatically on all Claude calls. The anthropic-beta: prompt-caching-2024-07-31 header and cache_control: { type: "ephemeral" } are sent with every Claude request. From the second generation, the system prompt (~400 tokens) costs $0.30/M instead of $3.00/M — a 90% reduction requiring zero user action.

        

      


      
      

        
Q7
Why was Gemini slow to start streaming, and how was it fixed?
▼

        

          
Gemini 2.5 Flash has built-in "thinking" (reasoning) enabled by default — it runs an internal reasoning pass before generating any output, during which the stream sends no text. This caused 0 words · 3–10s elapsed at the start.

          
Fix: thinkingConfig: { thinkingBudget: 0 } is sent on all Gemini calls. Document generation doesn't benefit from deep reasoning — streaming starts immediately and thinking tokens are not billed.

        

      


      
      

        
Q8
Why do refine and polish use a higher token budget than generation?
▼

        

          
Per-doc budgets (e.g. 3,500 for SOP) are sized for generating fresh output. Rewrite operations receive the full existing document as input and must output a complete rewrite — applying the same 3,500 cap to a 40,000-char input produces a truncated 19-word fragment.

          
Fix: all rewrite operations (refine, polish, Step 2 inject) temporarily use 8,000 tokens, then restore the per-doc budget for the next fresh generation.
